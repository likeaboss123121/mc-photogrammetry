## G1 — coverage no longer double-counts occluded or clipped area

Both of the lead's reproductions were independently reproduced first, exactly:
a broad `VISIBLE` polygon with a half-cell occluder reported
`visible=1.0, foreground_occlusion=0.49505, declared=visible`; a cell 90.1%
outside a 10px-wide image reported `visible=1.0, outside_image_fraction=0.90099,
declared=visible`. Both are wrong for the reason the review names: each label
was rasterized independently, and clipping normalized against the in-frame
crop rather than the cell's true full area.

Fix: `_label_masks` now builds one set of mutually exclusive boolean masks
(`VISIBLE`/`OPENING`/`FOREGROUND_OCCLUSION`/an internal `_conflict`) once per
call, bounded strictly by `image_size`. `OPENING` and `FOREGROUND_OCCLUSION`
are drawn over `VISIBLE`; their mutual overlap becomes `_conflict` and is
excluded from every label, so a genuinely contested pixel supports nothing.
`rasterize_cells` computes each cell's true full area in closed form (shoelace
formula, `_polygon_area`) rather than by rasterizing it — necessary because a
near-grazing cell can project to a quadrilateral spanning millions of pixels
even on a photograph a few thousand pixels wide, and rasterizing that extent
directly is both wrong (unbounded by the image) and slow. `CellEvidence` now
carries both `coverage_by_label` (fraction of the true full cell area — the
decision denominator) and `coverage_of_in_frame` (fraction of only the
in-frame portion — diagnostic only), plus `conflict_fraction`.

Reproduced after the fix: half-occluded case now gives
`coverage_by_label[visible]≈0.505, declared=None`; the clipped case gives
`coverage_by_label[visible]≈0.101, coverage_of_in_frame[visible]=1.0,
declared=None`. Four new tests in `test_footprint_adapter.py` lock in the
named scenarios directly: half-occlusion, 90%-clipping, an opening/occlusion
conflict (`conflict_fraction≈1.0`, neither label declared), and an extreme
grazing cell (a real projection found by walking `axis_directions(5,-3,2)`'s
column values, not a synthetic oversized region) that completes in under 2s
instead of allocating a raster sized to a million-pixel quad.

## G2 — adapter and exporter now agree on row/column-to-axis convention

Reproduced exactly: with axis Z, unit period, zero origin, cell
`(row=0, column=3)` has adapter lateral low corner `(3, 0)` but
`footprint.cell_to_block` exported block `(0, 3, 0)` — a straight
transposition that no existing test caught because every test cell used a
symmetric row=column value.

Fix: `cell_to_block` now builds `lateral = (origin[0] + column, origin[1] +
row)`, matching the adapter's `u = origin_u + column*period, v = origin_v +
row*period` convention (`others[0]` gets `column`/`u`, `others[1]` gets
`row`/`v`, `others` in ascending world-axis order — the same order
`lattice.plane_basis` uses). Added `block_to_cell`, the exact inverse, so
verification can start from a coordinate actually read back out of a real
litematic file rather than re-deriving from the in-memory footprint that
produced it — the gap the review named directly ("the overlay and scored
geometry must originate from the read-back volume, not the pre-export grid").

New tests: two independently hand-computed non-symmetric cases across
different axes/signs (`test_cell_to_block_matches_a_nonsymmetric_hand_computed_case_per_axis`),
a direct cross-check of `footprint.py` against the adapter's own convention
(`test_cell_to_block_agrees_with_the_adapters_own_lateral_convention`), and a
round-trip test (`test_block_to_cell_inverts_cell_to_block_exactly`).

### A detour: the litematic `Position` field is correct as it stands

While wiring up read-back verification, writing a block at `(3, -2, -1)` and
reading it back gave `(3, 0, 0)`, which looked like a second exporter bug —
`LitematicExporter.export` hardcodes `Position: (0,0,0)` regardless of the
volume's actual minimum corner. Editing that immediately broke
`tests/test_litematic.py` (`"single-region exports must use a zero local
position"`): this is a deliberate, tested invariant. A litematic is a
relocatable structure; a single region stores its shape local to its own
minimum corner, not an absolute placement, so `Position` is correctly always
`(0,0,0)` and the exporter needed no change — reverted, confirmed the 8
`test_litematic.py` tests pass again with the original file. The actual fix
belongs in code that reads litematics back: `footprint_pilot.py` and
`footprint_pilot_real.py` now compute the exported volume's own minimum
corner (from `{cell_to_block(footprint, cell) for cell in expected_cells}`)
and add that shift back to read-back local coordinates before calling
`block_to_cell`. `test_a_single_region_litematic_stores_shape_local_to_its_own_minimum`
locks this understanding in directly, exporting a set of cells that deliberately
excludes local `(0,0)` so the exported minimum is nonzero.

## G3 — the real pilot reports an honest status, not "resolved"

`footprint_pilot_real.py` is rewritten around the review's core objection:
marking the length low-confidence does not resolve phase, and reporting
`status=resolved` on that basis implied a validated reconstruction that
doesn't exist. Per the standing project rule that manual/assumed geometric
input is diagnostic, never production, `result.json`'s `status` is now one
of `length_unresolved`, `extent_behind_camera`, or `assumed_grid_diagnostic`
— never `resolved`.

Other changes to the bundle:

- `axis_alternatives` records every axis/side candidate considered (not just
  the first that resolved), with its status and distance, so the choice has
  visible provenance instead of being silently the first valid one.
- `continuous_region` — the bounds of the declared visible extent in
  real-world (u, v), computed before any grid is assumed — is now the
  primary, most defensible output, independent of whether phase/scale ever
  resolves.
- `lateral_origin=(0,0)` and `face_coordinate` are now recorded under a
  separate `export_convention` block with `lateral_origin_is_assumed_not_measured:
  true` and an explanatory note, making clear this is an arbitrary local
  export choice distinct from the continuous camera transform — not a
  workaround for any exporter defect, since the defect it was originally
  written to route around (see the `Position` detour above) doesn't exist.
- `annotation_sha256`, `calibration_artifact_sha256` and `source_image_sha256`
  are all persisted, closing the gap where the real bundle saved less
  provenance than the synthetic one.
- Read-back verification (the same shift-aware logic from the G2 fix) now
  runs against the real pilot's own exported file, not just the synthetic
  control.
- The overlay is stamped "HYPOTHETICAL GRID - phase not resolved, see
  result.json," and `result.json` states explicitly that `evidence.json`'s
  `supported_blocks`/`opening_cells` are a hypothetical discretization at an
  assumed, unresolved phase, not recovered exact cells.

The 53-block count is unchanged from the prior report; what changed is that

## What this establishes and does not

**Does:** G1 and G2 are independently reproduced and fixed with regression
tests keyed to the review's own numbers. Read-back verification — starting
from a litematic actually written to disk and reloaded, not the in-memory
grid that produced it — passes for both the synthetic bundle (10 blocks) and
the real pilot (53 blocks). The real pilot's bundle schema now matches the
synthetic one's completeness, and its status field no longer overclaims.

**Does not:** resolve real-world phase or scale for the pilot wall — that
remains explicitly unresolved, by design, per the review ("unresolved real
block phase/scale need not prevent" the C experiment that follows). Does not
touch A1 or reintroduce any texture cue into this geometry path.
