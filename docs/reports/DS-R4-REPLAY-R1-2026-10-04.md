## 1. Root cause (confirmed by evidence report)

`docs/reports/DS-IMG-SUPPORT-OWNERSHIP-R1-evidence-2026-10-04.md` established that
`image_derived_lattice_measure._replay_frame` rebuilt `ImageDerivedFrame` without
`ingress`, then compared `session_mod._frame_payload(replayed)` with the record
frame. The canonical `_frame_payload` includes the `ingress` key whenever the pin
is present (`image_derived_session.py:748-750`), so every `capture_ingress=True`
session failed lattice replay with `provenance_mismatch` / `session.frame`. The
accepted entry stage already carried the pin (`image_derived_entry.py:765-785`),
so this seam was the single producer/consumer gap.

## 2. Fix (exact diff)

Owned path: `src/mc_photogrammetry/pipeline/image_derived_lattice_measure.py`
(untracked in the working tree, so no git baseline; hunks shown literally).

```diff
@@ _replay_frame docstring @@
     the pixel digest; the rebuilt identity/shape/digest must then equal the frame
     the canonical record rebuilt.
+
+    The optional ingress pin is carried from the record frame, exactly as the
+    accepted M7 entry replay does, so a capture-enabled session's canonical frame
+    payload (which includes ``ingress`` when present) round-trips and validates;
+    the constructor re-checks the pin against this frame's id, shape and digest.

@@ reconstructed frame @@

+            image_sha256=frame.image_sha256,
+            # The ingress pin is identity-bearing metadata, not pixel data: carry
+            # the record's own canonical pin so the payload comparison below is
+            # exact.  The accepted frame constructor still re-validates that the
+            # pin names this frame, its shape and its pixel digest, so a

+            ingress=record_frame.ingress)
```

This mirrors the accepted entry precedent (`ingress=record_frame.ingress`). The
existing fail-closed checks are unchanged: the type check, the pixel-free branch,
the constructor immutable-`uint8`/shape/pixel-digest re-validation (and its
`provenance_mismatch` / `session.frame.pixels` refusal), and the canonical
`_frame_payload` equality are all preserved. With no pin the record frame carries
`ingress is None`, so the default payload is unchanged.

## 3. Focused tests added

Owned path: `tests/test_image_derived_lattice_measure.py`. Existing fixtures were
audited first; only synthetic in-memory scaffolding was added:

- `_build_session(..., ingress=False)` grew an optional pin path using the
  accepted `session_mod.build_image_derived_session(..., ingress=...)`.
- `_ingress_pin(...)` builds a real pin through
  `ingress_mod.build_frame_ingress_provenance` (no PNG/evaluator material).
- `_reading_signature(...)` compares measured reading content across sessions.

Four regressions, matching the assignment:

1. `test_an_ingress_bearing_session_replays_through_the_lattice_measurement` -
   capture-enabled session measures `assembled` with matching session/pose-graph
   digests and a sealed bridge (fails before the fix with
   `provenance_mismatch/session.frame`).
2. `test_a_mismatched_record_frame_ingress_pin_is_refused` - a forged record pin
   whose pixel digest disagrees with the retained frame is refused
   `provenance_mismatch` / `session.frame.pixels`.
3. `test_a_capture_enabled_session_binds_its_pin_to_the_signature_witness` - the
   session's own pin reaches the ordinary source-tap witness seam; the observed
   sink never refuses as if the pin were absent, while an otherwise identical
   no-ingress control refuses exactly `ingress_provenance_unavailable`.
4. `test_the_default_no_ingress_path_replays_with_unchanged_parity` - the default
   record carries no `ingress` key, replays with `ingress is None`, and an
   ingress-bearing session over the same pixels has identical calibrations and
   reading content; only the session-bound digest differs through the pin.

## 6. Out-of-scope finding (not fixed)

The requested capture-enabled witness test surfaced a **separate, pre-existing
condition** in an unowned module:
`src/mc_photogrammetry/pipeline/candidate_support_provenance.py:203` refuses any
witness whose `tap_source_indices` contains the documented `-1` border sentinel,
because it tests `< 0`; the sibling `cell_source_indices` check at line 208
correctly uses `< -1`, and `tests/test_signature_sampling_witness.py:33`
explicitly asserts `-1 in witness.tap_source_indices` for the accepted sampler.
Measured evidence from the real synthetic chain: the reading witness's
`rgb/coverage/region` `tap_source_indices` range `-1 .. 54638` against
`240*360 = 86400`, and all six sink entries return
`SourceTapWitnessRefusalV1(reason="source_tap_witness_index_out_of_range",
detail="tap_source_indices")` even though the session's ingress pin was carried
(control without the pin returns `ingress_provenance_unavailable`). Test 3
therefore asserts pin threading to the seam rather than a successful binding.
This was **not** edited, per the assignment's prohibition on touching signatures
or other pipeline modules; it needs a separate lead decision if real R1
signature/candidate-support capture is required downstream.
